# 智能入库SmartIngest - 需求分析

## 一、需求背景

现有系统已有独立的剪藏（Clip）、待办（Todo）、话题（Topic）三个模块，各自有独立的添加入口和表单。用户需要将任意文本粘贴后，系统自动识别文本意图并路由到对应模块入库，无需用户手动选择类型和填写字段。

核心痛点：
1. **手动选择类型繁琐**：用户需先判断文本属于剪藏/待办/话题，再找到对应入口填写表单
2. **字段填写费时**：每个模块需要不同字段（标题、优先级、截止日期、标签、分类等），手动填写效率低
3. **多入口分散**：三个模块各自独立，用户需记住多个入口位置
4. **AI 能力未充分利用**：已有 AI 分析能力但未用于自动分类和字段提取

## 三、用户场景

### 场景 1：默认流程——智能识别入库
用户粘贴一段文本，未指定类型：
- 用户输入"明天下午3点前完成报告，高优" → 系统识别为 todo → 提取 title/priority/deadline → 调用 `/api/todo/add` 入库
- 用户输入"TCP 三次握手过程详解..." → 系统识别为 clip → 提取 title/content/summary → 调用 `/api/clip/add` 入库
- 用户输入"推荐 Obsidian 这个笔记工具，功能强大" → 系统识别为 topic → 提取 title/summary/content → 调用 `/api/topic` 入库

### 场景 2：例外流程——用户指定类型
用户明确指定入库类型：
- 用户说"智能剪藏这个内容：xxx" → 走例外流程 → 调用 `POST /api/ingest`（只传 text，后端 AI 全权处理）
- 用户说"剪藏到话题：关于AI发展的讨论..." → 走例外流程 → 调用 `POST /api/topic`
- 用户说"添加待办：完成月报" → 走例外流程 → 调用 `POST /api/todo/add`
- 用户说"添加剪藏：保存这篇文章" → 走例外流程 → 调用 `POST /api/clip/add`

### 场景 3：降级处理
- 意图模糊无法确定 → 降级为 clip store-only 类型，使用原文作为 content
- 字段提取失败（如标题为空）→ 使用原文前 30 字作为 title
- 后端服务未启动 → 提示用户启动后端服务
- curl 超时 → 提示用户重试（3次重试+延迟0/2/5秒）

### 场景 4：浏览器插件智能入库
- 用户在浏览器中选中文本 → 右键菜单选择"智能入库" → 自动调用后端 API 入库
- 用户在插件弹出窗口中输入文本 → 点击"智能入库"按钮 → 调用后端 API 入库
- 输入内容过短（<5字符）→ 前端拦截提示"内容过短"

### 场景 5：前端页面智能入库
- 用户在 clip.html 页面 textarea 中输入文本 → 点击"智能入库"按钮 → 按钮显示"分析中..."加载态 → 调用 API 入库 → 显示识别结果 toast

### 场景 6：话题模块完整流程
- 用户创建话题（标题/摘要/分类/标签/Markdown内容）
- 用户从已有剪藏导入创建话题
- 用户浏览话题列表（卡片流：封面图/标题/摘要/标签/点赞数）
- 用户查看话题详情、点赞、编辑、删除
- 用户搜索和分类筛选话题

## 四、非功能需求

- **一致性**：SKILL.md 的意图规则需与后端 AiService.identifyIntent 的 systemPrompt 保持同步，两处规则变更时需同步修改
- **健壮性**：LLM 返回空字符串或非法值时有防御性降级处理；Git 操作失败仅打日志不影响主流程
- **可用性**：AI 处理耗时需有加载态反馈，防止用户重复点击
- **兼容性**：支持 Windows PowerShell 调用（Invoke-WebRequest + UTF-8 字节数组）
- **可维护性**：双AI路径架构文档化，标注维护风险和注意事项
