# CutShelter 数据层重构与用户习惯聚合开发计划

> 状态：按 TDD 分阶段实施  
> 更新日期：2026-08-03（L0 工作台只读骨架已完成）

## 目标

保留现有 JSON 业务数据和本地优先特性，新增可重建的统一索引、关系、项目和习惯统计层。该计划不建设 Agent 平台，不自动移动或修改用户数据。

## 重构顺序

1. **Phase 0：统一内容引用**
   - 定义 `ContentRef`、`ContentRelation` 和映射器。
   - 为剪藏、知识、待办、学习计划、编辑器文件建立稳定引用 ID。
   - 先兼容旧 JSON，不改变现有实体存储格式。
2. **Phase 1：只读内容索引**
   - 新增 `ContentIndexService`。
   - 扫描现有业务目录生成可重建索引。
   - 提供状态、重建和搜索接口。
3. **Phase 2：关系索引**
   - 统一 `sourceClipId` 和后续项目关系。
   - 支持来源链、反向查询和幂等关系写入。
4. **Phase 3：轻量项目模型**
   - 支持手动创建项目、加入内容、项目内搜索和默认偏好。
   - 不自动创建项目，不自动移动文件。
5. **Phase 4：用户行为事件**
   - 记录打开、编辑、保存、分类、标签、转换、项目关联等轻量事件。
   - 本地 JSONL，异步写入，默认保留 30～90 天。
6. **Phase 5：习惯画像**
   - 聚合常用分类、标签、目录、文件类型、动作和时间段。
   - 使用计数 + 时间衰减，不引入机器学习。
7. **Phase 6：项目聚合建议**
   - 根据标签、分类、目录、时间和连续操作生成可解释建议。
   - 用户确认后才建立项目关系，支持忽略和永久拒绝。

## 数据目录

```text
业务数据：{storagePath}/
  clip-storage/ todoList/ knowledge/ topic/ learning-plan/ vault/

应用索引：~/.cut-shelter/config/index/
  content-index.json
  relation-index.json
  projects.json
  project-memberships.json
  habit-profile.json
  action-events.jsonl
```

索引不是数据真相，损坏后必须可以通过业务目录重建。配置、行为数据和索引不得写入用户选择的业务数据目录之外的随机位置。

## TDD 约束

- 每个阶段先写失败测试，再实现最小代码。
- 映射、索引、关系和评分逻辑优先使用纯单元测试。
- 文件系统测试使用临时目录，不能读写用户真实数据。
- 重建操作必须幂等，失败不能影响编辑器和剪藏主流程。
- 自动建议必须包含原因、置信度、确认、忽略和永久拒绝状态。

## Phase 0 首批验收

- `clip:1001`、`knowledge:2001`、`todo:3001` 等引用 ID 稳定且类型明确。
- 标题、分类、标签、来源路径和创建时间能从现有实体正确映射。
- 缺失字段和旧 JSON 字段不会抛出异常。
- 相同实体重复映射结果一致。
- `ContentRef` 不携带正文，避免索引重复保存用户内容。

## 项目概念设计（下次开发前置约束）

当前软件没有“项目”概念，第一版项目定义为用户主动创建的轻量聚合工作视图，而不是新的文件夹、数据库或内容副本。项目只保存名称、描述、颜色、状态和成员引用；原始内容继续留在剪藏、知识、待办或编辑器文件中，项目删除或归档不得删除原始内容。

### 数据关系

```text
原始数据 → ContentRef（可重建索引） → ProjectMembership（用户确认的成员关系） → 项目工作视图
```

- `ContentRef` 描述内容是什么、在哪里、属于什么类型。
- `ProjectMembership` 描述内容是否被用户确认加入项目，以及 `source/reason/confidence`。
- `ContentRelation` 描述来源、引用和转换关系，不等同于项目成员关系。
- 一个内容可以属于多个项目；移除成员只删除关系，不修改内容。

### 第一版模型与生命周期

```text
Project: id(p_<uuid>), name(1～60), description(≤500), color, status(active/archived), createdAt, updatedAt
ProjectMembership: projectId, contentId(ContentRef.id), source(manual/suggestion/import), confidence, reason, createdAt
```

用户先手动创建空项目，再从内容详情、编辑器文件树或观测页加入内容。项目支持查看成员、移除成员、归档和删除；删除项目必须二次确认，只删除项目及成员关系。第一版不保存正文、规则或 AI Prompt，正式创建统一使用 `p_<uuid>`。

### 推荐边界

第一版不自动创建项目，也不因一次操作就推荐。只有存在 active 项目，且候选内容与已有成员在标签、分类、目录或近期操作上形成稳定重合时才展示建议。建议卡片必须包含目标项目、候选内容、评分、原因、加入和忽略操作；低于 0.55 不展示。用户确认后才写入成员关系，忽略支持冷却期和永久拒绝。

## 工作台方案修订版（已确认，2026-08-03）

本节以用户确认的偏好为准，覆盖前文仅以 `Project` 为中心的产品描述。用户已确认：

```text
工作台入口独立一级导航
项目是工作台的一种类型
默认所有内容可见
自动筛选与手动加入并存
学习模块未来作为特殊工作台接入
看板状态只在工作台内生效
```

### 一、最终产品理解

CutShelter 的核心不是“把内容放进项目文件夹”，而是把分散在不同模块中的内容，按用户当前目标组织成一个可操作的工作台。

```text
全部内容（默认视图）
  ├── 剪藏
  ├── 编辑器文件
  ├── 待办
  ├── 知识
  └── 学习计划
          │
          ▼
      工作台上下文
          │
          ├── 自动筛选内容
          ├── 用户手动加入内容
          ├── 来源/引用关系带入内容
          └── 工作台内看板状态
```

工作台上下文不是权限系统。用户始终拥有并可以访问全部内容；切换工作台只改变当前展示和操作上下文，不隐藏、复制、移动或删除原始内容。

### 二、工作台、项目、学习模块、看板的边界

#### 1. 工作台（Workspace）

工作台是产品层的统一容器，负责：

- 当前关注目标的筛选条件。
- 手动加入和排除的内容。
- 内容来源、类型和最近活动的统一展示。
- 工作台内的看板列和局部状态。
- 工作台级统计与建议。

工作台类型：

```text
general   普通工作台，适合临时整理或长期主题
project   项目工作台，适合有明确目标和交付结果的工作
learning  学习工作台，预留给学习模块成熟后的接入
```

第一阶段只开放 `general` 和 `project`，`learning` 只保留类型扩展点。

当前代码中的 `projects.json`、`project-memberships.json` 和 `ProjectIndexService` 属于已经落地的项目索引基础设施，不代表最终 UI 和产品模型已经完成；L0～L1 负责在不破坏这些旧文件的前提下增加 `Workspace` 兼容层。

#### 2. 项目（Project）

项目不再作为顶层产品容器，而是工作台的一种业务类型。项目可以有目标、描述、截止时间和交付状态，但这些字段只属于工作台，不改变原始内容模型。

前文已经实现的 `Project`、`ProjectMembership`、`ProjectIndexService` 是第一版索引基础设施。后续不立即删除或强制改名，而是通过兼容适配逐步迁移为：

```text
Project           → Workspace 的 project 类型
ProjectMembership → WorkspaceMembership 的兼容数据
ProjectIndex      → WorkspaceIndex 的底层实现
```

#### 3. 学习模块

学习模块目前功能不完整，不作为本轮工作台的前置依赖。未来学习模块可以创建 `learning` 类型工作台，并额外增加学习目标、阶段、复习计划、掌握度等字段；普通工作台不依赖这些字段。

学习工作台未来可以使用：

```text
待学习 → 学习中 → 待复习 → 已掌握
```

但这些状态只在学习工作台内有效，不同步覆盖待办完成状态或剪藏业务状态。

#### 4. 看板（Board）

看板是工作台内的处理视图，不是独立的数据归属系统。看板列表示“在这个工作台里如何处理”，而不是“原始内容当前是什么状态”。

普通项目默认看板：

```text
收集 → 处理中 → 已完成
```

学习工作台默认看板：

```text
待学习 → 学习中 → 待复习 → 已掌握
```

同一内容加入两个工作台后，可以在两个看板中拥有不同状态，不能互相污染。

### 三、工作台入口与页面结构

主导航增加独立一级入口，位置固定为：

```text
编辑 | 工作台 | 剪藏 | 话题 | 密码 | 学习 | PDF | 观测 | 设置
```

工作台页面第一版结构：

```text
左侧：工作台列表
  全部内容
  最近使用
  我的工作台
  新建工作台

中间：当前工作台内容
  工作台标题与描述
  内容类型筛选
  搜索框
  看板 / 列表切换
  内容卡片

右侧或抽屉：工作台设置
  自动筛选条件
  默认看板
  工作台颜色
  归档与删除
```

第一版不把工作台入口放进学习模块，也不把工作台嵌入剪藏页面。剪藏页面保留独立入口，后续增加“当前工作台内容”筛选和“加入工作台”操作。

### 四、内容进入工作台的三条通道

工作台内容集合使用并集计算：

```text
当前内容 = 规则命中内容 ∪ 手动加入内容 ∪ 关系带入内容 − 用户排除内容
```

#### 1. 自动规则

用于低成本聚合已有内容，支持：

- 内容类型：clip / knowledge / todo / file / learning-plan。
- 分类匹配。
- 标签包含或排除。
- 文件目录包含。
- 工作流状态匹配。
- 创建时间或最近更新时间范围。

规则命中只是展示结果，不建立永久成员关系。规则更新后，工作台内容随索引变化。

#### 2. 手动加入

用户在内容详情、编辑器文件树、待办详情或工作台页面点击“加入工作台”。手动加入内容即使不满足规则，也必须保留在工作台中。

#### 3. 关系带入

内容存在来源剪藏、转换、引用等 `ContentRelation` 时，可作为关联内容展示，但默认不直接写入永久成员关系。用户确认后才转为手动成员。

#### 4. 用户排除

如果内容被规则命中但用户不希望看到，需要保存工作台级排除记录。排除优先级高于规则和关系带入，避免用户反复被推荐。

### 五、建议数据模型

产品层最终建议采用以下模型；现有 `Project*` 模型通过迁移适配，不一次性破坏旧索引。

```text
Workspace
  id              w_<uuid>
  name            1～60 个字符
  type            general / project / learning
  description     ≤500 个字符
  color           主题色
  status          active / archived
  createdAt
  updatedAt

WorkspaceRule
  id              r_<uuid>
  workspaceId
  field           type / category / tag / sourcePath / workflowStatus / updatedAt
  operator        equals / contains / in / before / after
  value
  enabled
  createdAt

WorkspaceMembership
  workspaceId
  contentId       ContentRef.id
  source          manual / rule / relation / import
  boardColumnId   工作台内看板列，可为空
  position        工作台内排序
  reason          加入原因
  confidence      0～1，可为空
  createdAt
  updatedAt

WorkspaceExclusion
  workspaceId
  contentId
  reason
  createdAt

BoardColumn
  id
  workspaceId
  key
  name
  position
  isDefault
```

关键约束：

- `ContentRef` 仍然是内容索引，不保存正文。
- `WorkspaceMembership` 不复制内容，只保存关联和工作台局部状态。
- `boardColumnId` 不能映射回原始待办状态或剪藏状态。
- 一个内容可以加入多个工作台。
- 删除工作台只删除规则、成员、排除项和看板配置，不删除内容。
- 归档工作台保留历史数据，但不参与新的自动推荐。

### 六、数据观测页的长期升级

现有数据观测页是索引健康和基础画像面板，后续升级为“数据层控制台”，但不变成业务工作台。

#### 当前已有

- 内容、关系、项目、成员和事件数量。
- 常用分类、标签、最近动作。
- 活跃日和最近活动。
- 内容索引重建。
- 深色主题适配。

#### 后续新增四个区域

1. **索引健康**
   - 各索引文件是否存在。
   - 最后重建时间、数据量、文件大小。
   - 自动同步状态、最近失败原因。
2. **埋点管道**
   - 近 7/30 天事件量。
   - 坏行数量、写入失败数量、清理时间。
   - 最近事件类型分布。
3. **工作台数据流**
   - 规则命中数量。
   - 手动加入数量。
   - 关系带入数量。
   - 用户排除数量。
   - 每个工作台的内容类型分布。
4. **建议效果**
   - 待确认、已接受、已忽略、永久拒绝数量。
   - 推荐采纳率。
   - 按原因统计的采纳率。
   - 最近重复推荐和冷却中的候选。

观测页只提供诊断和维护操作；“加入工作台”“移动看板列”等业务操作仍在工作台页面完成。

### 七、数据埋点规范

事件只用于本地聚合、建议和问题诊断，不上传云端，不写正文、API Key、密码或完整文件内容。

统一结构：

```json
{
  "eventId": "e_<uuid>",
  "eventType": "content_opened",
  "contentId": "clip:101",
  "workspaceId": "w_<uuid>",
  "source": "editor",
  "metadata": {
    "category": "编程",
    "contentType": "clip"
  },
  "createdAt": "2026-08-03T12:00:00",
  "schemaVersion": 1
}
```

第一批事件：

```text
content_created
content_opened
content_edited
content_deleted
content_tagged
todo_completed
workspace_viewed
workspace_member_added
workspace_member_removed
workspace_excluded
board_column_changed
suggestion_shown
suggestion_accepted
suggestion_ignored
suggestion_rejected
```

采集约束：

- 业务写入成功后再记录事件，不能因为埋点失败回滚业务操作。
- 事件写入异步化，单条事件失败只记录日志。
- `eventId` 幂等，重复重放不能重复计数。
- JSONL 坏行跳过并记录诊断计数。
- 默认保留 90 天，可在观测页主动清理。
- 事件读取默认只返回聚合结果，原始事件导出需要用户主动操作。

### 八、项目/工作台数据流

```text
用户创建工作台
    ↓
WorkspaceIndex 保存工作台和规则
    ↓
用户打开工作台
    ↓
ContentIndex 查询候选内容
    ↓
WorkspaceResolver 合并：规则 + 手动成员 + 关系带入 - 排除项
    ↓
返回去重后的 ContentRef 列表
    ↓
用户加入/排除/移动看板列
    ↓
写入 WorkspaceMembership / WorkspaceExclusion / boardColumnId
    ↓
记录行为事件
    ↓
观测页聚合数据，推荐服务生成下一轮候选
```

推荐服务不得直接写入工作台成员。它只能产生：

```text
SuggestionCandidate
  suggestionId
  workspaceId
  contentId
  score
  reasons
  expiresAt
  status
```

用户确认后才执行：

```text
SuggestionCandidate(accepted)
  → WorkspaceMembership(source=suggestion)
  → suggestion_accepted event
```

### 十、TDD 交付顺序

每个 L 阶段都必须遵循：失败测试 → 最小实现 → 定向测试 → 全量回归。

1. 先测试 `WorkspaceResolver`：规则并集、手动加入、关系带入、排除优先和去重。
2. 再测试工作台存储：创建、更新、归档、删除保护、成员幂等和跨工作台成员。
3. 再测试看板状态：局部状态隔离、排序稳定、原始业务状态不被修改。
4. 再测试事件管道：统一 schema、幂等、异步失败降级、坏行跳过和 90 天清理。
5. 再测试观测聚合：空数据、时间窗口、来源分布、趋势和采纳率。
6. 再测试建议状态机：稳定 ID、阈值、接受/忽略/拒绝、冷却期和确认后写关系。
7. 最后进行桌面/浏览器双模式冒烟，确认主题、路由、后端不可用和索引重建体验。

### 十一、长线完成标准

- 用户默认可以浏览全部内容，不需要先创建工作台。
- 工作台能够统一展示剪藏、文件、待办、知识和未来学习内容。
- 工作台筛选、手动加入、关系带入和排除行为可解释、可撤销。
- 看板状态只属于当前工作台，不污染原始内容。
- 观测页能解释索引、埋点、工作台和建议数据的来源。
- 埋点失败、索引损坏、后端暂不可用都不阻塞编辑和剪藏主流程。
- 推荐永远需要用户确认，不自动创建工作台、不自动移动内容。
- 学习模块可以后接入，但不需要重写工作台基础设施。
