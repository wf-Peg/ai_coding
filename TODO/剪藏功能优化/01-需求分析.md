# 剪藏功能优化 - 需求分析

## 一、需求背景

剪藏模块经过多轮迭代后，累积了以下待优化点和 Bug：

1. **剪藏详情空态误导**：详情页显示"内容处理中..."但实际是终态，AI 分析同步完成，不存在"进行中"状态
2. **来源链接不直观**：sourceUrl 存在但未展示为可点击链接，"查看"按钮打开编辑器而非原文
3. **源文件打开路径错误**：wiki-link 点击后报错，未拼接到实际文件路径
4. **Web Clipper 同步内容存储不完整**：content 只存 wiki-link，导致 AI 分析无法获取原文
5. **列表数据混入**：剪藏列表展示待办事项数据
6. **图片上传体验不佳**：类型控制不严格，粘贴/上传功能缺失，UI 样式问题
7. **缺少自动 Git 同步**：整理/周报后需手动提交变更
8. **多个功能 Bug**：展开收起、渲染、弹窗、导航等 11 个 Bug

## 三、用户场景

### 场景 1：查看剪藏详情
用户展开一条剪藏，看到 AI 分析区域：
- AI 分析成功 → 正常展示 Markdown 内容
- AI 分析失败 → 显示失败状态 + "重新生成分析"按钮
- 结构化内容跳过 AI → 显示中性空态 + "生成分析"按钮
- store-only 类型 → 不显示 AI 分析区域

### 场景 2：查看原文
用户展开剪藏详情，点击"查看原文"按钮 → 在新窗口打开来源 URL
用户点击来源链接 → 在新窗口打开来源 URL
内容超长 → 显示省略号截断，可展开查看完整内容

### 场景 3：打开源文件
用户展开剪藏，点击文件路径 → 编辑器以新标签打开实际源文件（Markdown 文件）

### 场景 4：Web Clipper 同步
用户通过 Obsidian Web Clipper 剪藏网页 → 同步后：
- 列表显示剪藏项
- 展开后原文区域显示正文内容（非 wiki-link）
- 能看到原始 URL 和文件路径
- AI 整理能正常分析正文内容

### 场景 5：图片上传
用户创建剪藏时：
- ai-text / store-only 类型 → 可上传/粘贴图片
- link-ai / doc-ai 类型 → 隐藏图片上传区域
- 粘贴图片 → 自动生成 Markdown 引用
- 删除图片 → 同时删除正文中的 Markdown 引用

### 场景 6：列表过滤
用户打开剪藏列表 → 只看到剪藏内容，不包含待办事项

### 场景 7：自动同步
用户执行整理今日内容或生成周报总结 → 自动执行 git pull/commit/push

## 四、非功能需求

- **兼容性**：前端三份源码（frontend/clip.html、browser-extension/clip.html、browser-extension/clip-main.js）同步修改，保持一致行为
- **安全性**：Git 操作失败仅打日志，不影响主流程
- **性能**：列表过滤不影响加载速度；Wiki 页面懒加载
- **可维护性**：三态模型 helper 函数在三份文件中保持一致实现
