# 设计文档：SQLite本地索引层M3（图谱关系层）

## 架构设计

```
Electron 主进程 Node 侧（electron/sqlite/）
  ├─ scanner.js          实体扫描（candidateRoots 双根探测：同级 / 内嵌 clip-storage）
  ├─ indexer.js          upsertEntity 实体索引、pruneMissing(按 type)、entityId
  ├─ relation-builder.js 三类关系构建 + refIds 归一化 + 遗留合并
  ├─ graph.js            getGraph 图谱组装 / relationsFor 反链
  ├─ index-service.js    indexEntities 编排（扫描→upsert→prune→重建关系）
  └─ init.js             schema v2：content(FTS5) + relation
        │
        ├─ main.js  ipcMain.handle : local-index:graph / local-index:relations / local-index:status
        └─ preload.js  contextBridge → window.electronAPI.localIndex.graph/relations
              └─ 前端 knowledge-graph.js 本地优先渲染，失败回退后端 REST
```

## 技术方案

- **数据源**：`content` 表新增 type=knowledge / learning-plan 实体，共用 FTS；`relation` 表存关系边。
- **实体 id**：`{type}:{id}`（如 `knowledge:39`、`plan:3`），对齐前端图谱节点 id。
- **关系三型**：`derived_from`(clip→knowledge 来源)、`linked_to`(knowledge↔knowledge)、`plan_links`(plan→knowledge/clip)。
- **重建策略**：`buildRelations` 先 `DELETE FROM relation` 再幂等写入；遗留 `index/relation-index.json` 每次重建后合并（ON CONFLICT DO NOTHING），保证迁移持久化。

## 接口定义

| IPC | 参数 | 返回 |
|---|---|---|
| `local-index:graph` | `{includeTypes}` | `{success, nodes[], links[]}` |
| `local-index:relations` | `{id}` | `{success, relations[]}` |
| `local-index:status` | - | 索引状态 + `relationCount` |

前端 `apiClient.fetchGraph({includeTypes})` / `relations({id})` 发言，`knowledge-graph.js` 的 `fetchData` 优先走本地 IPC。

## 关键决策

1. **实体路径双探测**：真实数据 knowledge/learning-plan 内嵌在 clip-storage 下，单测用同级布局；`candidateRoots` 同时探测两处并去重。
2. **字段兼容**：旧知识模型标量 `sourceClipId`，新模型 List `sourceClipIds`；`refIds` 取并集兼容。
3. **遗留迁移持久化**：弃「一次性迁移+meta 防重」，改为每次 rebuild 都合并遗留文件（幂等），符合「文件为真、库为缓存」。
4. **关系计数字段**：节点附带 linkedCount(出边)/sourceCount(入边)，plan 附加 phaseCount。
