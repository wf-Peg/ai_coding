# 设计文档：画布手绘墨迹持久化（多文档隔离）

## 架构设计

```
Electron 主进程 Node 侧（electron/）
  ├─ sqlite/canvas-ink.js    新增：墨迹层 CRUD（listInk / saveInk / clearDoc / clearAll / countInk）
  ├─ sqlite/init.js          schema v8：canvas_ink 表 + idx_canvas_ink_doc
  ├─ sqlite/canvas-doc.js    deleteDoc 级联清理该文档墨迹
  ├─ canvas-sync.js          快照 v3：buildSnapshot / restoreSnapshot / wipe 纳入 ink，兼容 v2
  └─ main.js                 canvas:state 返回 ink；新增 canvas:save-ink；写后 2.5s 节流推送
        │
        ├─ preload.js        contextBridge → window.electronAPI.localIndex.saveCanvasInk
        └─ 前端 canvas.js    strokes 带 id；按 docId 载入；400ms 防抖落库；切文档前 flush
              │
              └─ backend CanvasStateService.java  默认快照补 ink 字段（仅透传，无逻辑）
```

## 数据模型

```sql
CREATE TABLE IF NOT EXISTS canvas_ink (
  id         TEXT PRIMARY KEY,
  doc_id     TEXT NOT NULL,
  color      TEXT,
  width      REAL,
  opacity    REAL,
  points     TEXT NOT NULL,   -- JSON：[[x,y],...]（世界坐标）
  sort_index INTEGER,
  created_at TEXT,
  updated_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_canvas_ink_doc ON canvas_ink(doc_id, sort_index);
```

**为什么一笔一行、points 存 JSON 文本**：一笔的点永远是整笔读写，不存在「按点查询 / 按点更新」的需求。拆成 `canvas_ink_point` 点表会把「读一笔」变成 N 行 join、「写一笔」变成 N 次 insert，收益为负。JSON 文本是 SQLite 存小数组的常规做法，且与前端 `strokes[].points` 结构一一对应，序列化零转换。

**为什么需要 id**：前端 `strokes[i]` 目前无 id，无法与库中行对账。新增 `id = 'ink:' + base36(ts) + ':' + rand6`（不引依赖）。id 只用于库内主键与跨设备对账，前端渲染不依赖它。

## 接口定义

| IPC | 参数 | 返回 |
|---|---|---|
| `local-index:canvas:state` | `{docId}` | 原有字段 + **`ink[]`** |
| `local-index:canvas:save-ink` | `{docId, strokes}` | `{success, saved, truncated?}` |

preload：`window.electronAPI.localIndex.saveCanvasInk({docId, strokes})`。

**决策：墨迹并入 `canvas:state`，而非独立 `list-ink`。** 理由：画布状态本就是「一次取该文档全量」（nodes/edges/groups/layout 都在同一次返回），墨迹同属该集合；合并后 `loadData()` 仍是单次 await，且天然复用 docId 解析与 success 兜底。代价是 payload 变大，由「2px 抽稀（已有）+ 单文档笔迹上限 800」控制。若日后墨迹量大到需要分块/懒加载，再拆独立 IPC（届时 `canvas:state` 去掉 `ink` 字段即可，向后兼容）。

## 落库策略：整文档全量替换

`saveInk(db, docId, strokes)`：事务内 `DELETE FROM canvas_ink WHERE doc_id = ?` → 批量 INSERT → `canvasDoc.touch(db, docId)`。

**为什么不做增量 diff**：墨迹的写操作只有「整笔增 / 整笔删 / 撤销弹出一笔 / 清空」四种，不存在「改一笔内部某几个点」的场景。全量替换实现最简、状态最一致（不会出现库与内存分叉），单文档笔迹量级（几十~几百笔）下开销可忽略。事务包裹保证不出现「删完没写进去」的空窗。

**两层限流，作用不同**：
- `markInkDirty()` → 400ms 防抖 → `saveCanvasInk`（本地 SQLite 落库），避免连续作画时逐笔往返 IPC。
- `saveInk` 成功后触发快照同步，但走 **2.5s 节流**推后端（手绘高频，不与节点编辑共用 400ms `schedulePush`）。

**触发落库的时机**（缺一不可）：
1. `handleDrawEnd` 收笔后
2. `eraseAt` 命中擦除后
3. `Ctrl+Z` 撤销（`strokes.pop()`）后
4. 清空画布后（清空也是状态变更，需立即落库）
5. 切换文档前（`flushInk()`，把待落库的立即写盘）
6. 页面卸载/隐藏前（`beforeunload` / `visibilitychange`），避免关窗丢最后一笔

## 数据流

**载入**：`loadData()` 拿到 `canvas:state` → 处理 `allNodes` → 映射 `res.ink` 到 `strokes` → `ensureInkLayer()` → `renderInk()`。
注意 `renderInk()` 内部有 `if (!inkLayer) return`，而 `inkLayer` 只在 `renderCanvas()` / `ensureInkLayer()` 里创建。**空文档（无任何节点）路径要单独处理**：该分支下不会走 `renderCanvas()`，若要显示墨迹必须显式 `ensureInkLayer()` 并隐藏空态。

**切换文档**：`switchDoc()` 顺序必须是 ① `flushInk()`（立即落库）→ ② `strokes = []` → ③ `CanvasOutline.reset()` → ④ `await loadData()`。顺序错会丢掉最后一次防抖窗口内的笔迹。

**删除文档**：`canvas-doc.js` 的 `deleteDoc` 事务内补 `DELETE FROM canvas_ink WHERE doc_id = ?`，否则删文档后墨迹残留在库里，下次同步会被当作有效数据带回（**幽灵墨迹**）。

## 快照 v3

- `SNAPSHOT_VERSION` 升到 3；`buildSnapshot` 增加 `ink` 数组（每笔带 `docId`）。
- **`updatedAt` 计算必须纳入 ink**：现在取 `docs/nodes/groups` 三者 `updated_at` 最大值；若不纳入 ink，则「只画了笔迹、没动节点」时快照时间戳不前进，`pullSnapshot` 的 last-write-wins 比较会认为本地没更新，墨迹推不上去。同时 `saveInk` 内 `canvasDoc.touch(docId)` 刷新文档时间戳，双重保证。
- `restoreSnapshot`：`ink` 缺失（v2 快照）→ 视为空数组，保证 **v2 快照可正常恢复**；`docId` 不在快照 `docs` 内 → 归 `doc:default`；`points` 做合法性校验（数组、元素为长度 2 的有限数数组），非法笔迹**跳过而非整批失败**。
- `wipe()` 必须补 `canvasInk.clearAll(dbConn)`：否则 pull 覆盖本地时，快照里没有的旧墨迹会残留 → **幽灵墨迹**。这是本批最容易漏的正确性点。
- `CanvasStateService.java`：`readState` 的 `putIfAbsent` 与 `defaultSnapshot()` 补 `ink` 空数组；`DEFAULT_SNAPSHOT_VERSION` 提到 `"3"`。服务端仍不解析内部结构，纯透传。

## 关键决策

1. **并入 `canvas:state` 而非独立 IPC**：少一次往返、复用 docId 解析与成功兜底；**配合单文档笔迹上限 800** 控制 payload。
2. **整笔行 + points JSON + 整文档全量替换**：贴合墨迹的增删语义，实现最简、状态最一致。
3. **每笔补稳定 id**：编排落库与跨设备对账的前置条件。
4. **`updatedAt` 纳入 ink，且 `saveInk` 内 touch 文档**：避免「只画不改节点」时快照时间戳不前进而被 last-write-wins 吞掉。
5. **`wipe()` 清墨迹 + `deleteDoc` 级联清墨迹**：两处都做，杜绝幽灵墨迹。
6. **容量保护**：沿用前端已有的 2px 抽稀；后端 `saveInk` 单文档笔迹上限 **800**（超限截断最旧的并返回 `truncated`），避免 `canvas:state` payload 与快照体积膨胀。
7. **同步走 2.5s 节流**：手绘高频，`save-ink` 后的快照推送与节点编辑的 400ms `schedulePush` 分开，用更长节流降低全量快照 POST 频率。

## 风险与取舍

| 风险 | 说明 | 处理 |
|---|---|---|
| 快照体积膨胀 | points 为采样点，长笔迹点数多 | 已有 2px 抽稀 + 单文档笔迹上限；必要时后续引入 Douglas–Peucker |
| 幽灵墨迹 | restore 前未清空本表 | `wipe()` 补清 `canvas_ink`；`deleteDoc` 级联清 |
| 丢最后一笔 | 切文档时防抖窗口未 flush | `switchDoc` 首步 `flushInk()`；卸载前再 flush |
| 空画布墨迹不可见 | 无节点时空态分支 `showEmpty + return`，连 SVG/`ink-layer` 都不建，空态遮罩还会挡住墨迹 | 载入墨迹后显式建 SVG + `ensureInkLayer()` 并隐藏空态（fp-005 单列专项子任务） |
| 墨迹同步被吞 | 只画笔迹时 updatedAt 不变 | ink 纳入 updatedAt + `saveInk` 内 touch 文档 |
| 仍不进大纲/Markdown | 本批定位是「不丢 + 隔离 + 同步」 | 在 04 验收清单「范围边界确认」显式标注，避免误判为缺陷 |
| 跨版本混跑丢墨迹 | v2 设备 pull 到 v3 快照会忽略 ink，再 push 无 ink 快照覆盖后端 | 验收显式约定「同步假定两端同版本」；属 canvas-sync 全量 last-write-wins 固有边界 |
