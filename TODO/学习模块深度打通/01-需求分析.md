# 需求分析：学习模块深度打通

## 原始需求

调研学习模块，探索与剪藏、知识、编辑器的关系，深度打通串联各模块，借鉴 Obsidian、Notion 等优秀软件的思路与设计。

## 分析结论

- 学习计划模块目前是孤岛：仅做学习计划 CRUD、阶段进度、掌握度与导出，与剪藏、知识、编辑器无字段级关联，不参与「剪藏 → 知识 → 图谱」数据流。
- 底层已有可复用机制：图谱 GraphService 支持类型化边、知识已有 [[wikilink]] 双链、编辑器已有 openTextData 新标签打开通道、index.html 已有 postMessage 导航体系。
- 方案：借鉴 Obsidian 双链/反链/全库图谱 + Notion 数据库关联，以阶段级关联为核心打通：
  1. 学习计划 ↔ 知识/剪藏（阶段关联）
  2. 知识/剪藏 反链（被学习计划引用）
  3. 学习计划节点 + plan_links 边入图谱
  4. 编辑器打开阶段说明

## 范围确认

- 核心打通（不含学习日志/打卡，避免过度复杂）
- 编辑器联动为「编辑器中打开阶段说明」（单向打开，不做双向同步）

## 实施与回归记录

- 阶段级关联、反链查询、图谱 plan_links、前端关联区块与反链区块、导航路由全部实现并推送。
- 回归验证发现并修复图谱 links 恒为 0 的 bug：图谱节点来自 content-index.json（旧 KnowledgeEntry），边来自 relation-index.json（主模型 Knowledge），两套 ID 体系不一致。修复方案：ContentRefMapper 新增 fromKnowledgeBase(Knowledge)，ContentIndexService.rebuildFromStorage 改用 getAllKnowledge() 统一知识源，重建索引后 derived_from / linked_to / plan_links 边全部正常渲染。
- 验收：学习计划列表正常、阶段关联更新正常、by-knowledge / by-clip 反链正常、GET /api/graph 返回 learning-plan 节点与三类边。测试数据已清理。
