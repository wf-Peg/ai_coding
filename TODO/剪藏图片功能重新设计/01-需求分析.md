# 剪藏图片功能重新设计 - 需求分析

## 一、需求背景

现有剪藏图片功能为多轮迭代拼凑产物，经代码审计确认存在系统性缺陷（详见问题清单）。图片在剪藏列表/详情中**无法显示**（引用 URL 无后端端点），前端主页面已禁用图片上传，传输方式（base64）、存储归属（clip-organized 异根）、整理链路（正则丢路径）、生命周期（无清理）均需重构。

## 二、现状问题清单（代码实证）

| # | 问题 | 实证位置 |
|---|------|----------|
| 1 | 图片 URL `/api/clip/image/{category}/{file}` **无后端端点**，界面图片全部 404 | ImageUtils.generateRelativePath 生成该 URL；全后端无对应 controller 映射 |
| 2 | 前端页面已禁用图片（注释"图片上传功能已关闭"），仅扩展端在用 | frontend/clip.html:3279 |

## 三、用户场景

### 场景 1：粘贴/上传图片
用户创建剪藏（ai-text/store-only）时：
- 直接粘贴剪贴板图片（截图等）→ 自动压缩 → 上传 → **在光标位置**插入图片引用
- 点击上传按钮批量选择图片 → 逐个上传（显示进度）→ 插入引用
- 缩略图预览，可单独删除（同时移除内容中的引用）

### 场景 2：查看剪藏
- 剪藏详情展开后，原文中的图片**正常显示**（不再 404）
- 剪藏列表可显示小缩略图（可选）

### 场景 3：删除与清理
- 删除剪藏 → 其引用的图片文件被清理（未被其他剪藏引用时）
- 手动触发孤儿图片清理

### 场景 4：整理导出
- 执行"整理今日内容"后，生成的 Markdown 中图片引用正确，Obsidian 打开可见（`./assets/{uuid}.{ext}`）

### 场景 5：doc-ai 附件
- 文档类剪藏的源文件独立存储、可下载，不与图片混用

### 场景 6：旧数据迁移
- 存量剪藏（content 含旧 `/api/clip/image/...` 引用、图片在 clip-organized/assets）迁移后引用与文件正常

## 四、非功能需求

- **兼容性**：前端（frontend/clip.html）与扩展（browser-extension/clip-main.js）行为一致；旧 base64 imageDataList 兼容解析
- **性能**：客户端压缩后再上传（体积降 5-10 倍）；上传有进度；列表缩略图可选
- **安全性**：上传 magic-byte 校验（非仅扩展名）；读取路径穿越防护（文件名白名单 + normalize + 限定根目录）
- **可维护性**：图片存储与分类/整理状态解耦（UUID 命名、按月分片）；`imagePaths` 为权威引用清单
- **不引入新依赖**：canvas 压缩用浏览器原生，后端缩略图用 JDK ImageIO；webp 由客户端转 jpg/png 规避
