# 需求分析：软件更新优化与分发渠道调研

## 原始需求

1. 调研目前应用设置里面的软件更新逻辑（设置页「软件更新」区块）
2. 优化升级逻辑（检查、下载、应用全链路）
3. 更新打包脚本：提示是否要增加版本号并更新
4. 探索更新服务的实现：除 GitHub 外是否有其他免费发布服务支持上传安装包供用户下载（GitHub 国内请求速度太慢）

## 分析结论

### 现状链路

设置页 `frontend/settings.html`（index.html iframe）→ `frontend/js/settings.js` → `electron/preload.js` IPC → `electron/main.js`（`checkForUpdates` / `download-and-apply-update`）→ 后端 `UpdateController` `/api/update/check` → GitHub Releases API → 返回版本/下载地址 → 前端展示 → 下载 ZIP（`update-manager.downloadUpdate`）→ `applyUpdate` 解压替换 `resources/` → 重启。

### 发现的问题

| # | 问题 | 证据 |
|---|------|------|
| 1 | 更新包 232.6MB 虚胖：含版本间不变的 `jre/`(61MB)、无引用的重复 JAR `frontend/clip-backend.jar`(88MB) | 实测 zip 内容与体积 |
| 2 | **致命 Bug**：旧打包脚本 zip 无 `resources/` 顶层目录，`applyUpdate` 按 `extractDir/resources` 查找 → 更新实际是空操作 | 实测 zip 顶层条目 + 代码核对 |
| 3 | 命名不一致：`build-update-zip.js` 产出 `clip-update-v1.0.7.zip`，`release.bat` 产出 `clip-update-1.0.7.zip` | 代码核对 |
| 4 | `fetchLatestRelease` 死代码（main.js 从未调用，检查走后端）；本地版本缓存无人使用 | grep 核对 |
| 5 | 后端手工字符串解析 JSON（indexOf），脆弱；无缓存、无认证、无校验值 | 代码核对 |
| 6 | GitHub 国内慢：检查打 `api.github.com`、下载打 `objects.githubusercontent.com`，无国内兜底 | 用户反馈 + 调研 |
| 7 | 静默自动检查仅向 mainWindow 发事件，用户不在设置页看不到 | 代码核对 |
| 8 | `saveUpdateConfig` 整体覆写，前端保存会抹掉 `lastCheck` 等字段 | 代码核对 |

### 目标

更新包 ≤ ~100MB、结构正确；下载多源回退 + SHA-256 校验；后端检查带缓存；发布脚本交互确认版本号；产出分发渠道调研文档（本期不做 Gitee 分发）。
