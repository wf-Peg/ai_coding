# 设计文档：软件更新优化与分发渠道调研

## 架构设计

```
GitHub Releases（权威源，发布主流程：gh release create 上传 exe/dmg/AppImage/zip/sha256）
        │
        ▼
客户端检查：后端 /api/update/check（10 分钟缓存）──不可达──▶ 客户端直连 GitHub API（checkLatestRelease）
        │
        ▼
客户端下载：GitHub 原地址 ──失败──▶ gh-proxy 镜像1 ──失败──▶ 镜像2 ...（buildDownloadCandidates 按序回退）
        │                    （下载后 SHA-256 校验，失败删文件中止）
        ▼
applyUpdate：仅替换更新包内存在的 resources 顶层条目（jre/、*.log 保留）→ 重启
```

## 技术方案

### 1. 更新包瘦身（fp-001）

- `package.json` extraResources.frontend filter 追加 `!**/clip-backend.jar`；删除实体文件（untracked）。
- `scripts/build-update-zip.js`：staging 目录组装 `resources/`（含 app.asar、app.asar.unpacked、backend/、frontend/、TODO/），剔除 `jre/`（`--with-jre` 全量）与 `frontend/clip-backend.jar`；Windows 用 `Compress-Archive -Path '<stagingResources>'`（传入目录本身 → 生成 resources/ 顶层），Unix 用 `zip -rq out.zip resources`；输出 `clip-update-{version}.zip` + `{hash}  filename` 格式的 `.sha256`。
- 关键：**zip 顶层必须包含 `resources/`**，与 `applyUpdate` 的 `extractDir/resources` 预期一致。

### 2. 客户端链路（fp-002）

- `update-manager.js`：
  - 删除 `fetchLatestRelease`/`loadVersionCache`/`saveVersionCache` 死代码；保留 `checkLatestRelease`（直连 GitHub 降级，代理优先 + GH_TOKEN）。
  - `downloadUpdate(url, onProgress, expectedSha256)`：下载完成后 `crypto.createHash('sha256')` 校验，不匹配删文件抛错。
  - `buildDownloadCandidates(downloadUrl)`：`[{url: 原地址, name: 'GitHub'}, ...镜像前缀拼接]`；镜像前缀默认 `DEFAULT_MIRROR_PREFIXES`（ghproxy.com / mirror.ghproxy.com / ghfast.top），`update-config.json` 的 `mirrorUrls` 覆盖优先。
  - `downloadUpdateWithFallback(candidates, onProgress, expectedSha256)`：按序尝试，单源失败自动切换，进度回调携带 source 名（percent=0 表示切换、-1 表示该源失败）。
  - `applyUpdate`：改为仅替换 zip 内 `resources/` 顶层条目（文件用 copyFileSync、目录用 copyDir），`*.log` 保留，包外条目（jre/）不动。
  - `saveUpdateConfig`：合并写入 `{...existing, ...config}`。
- `main.js`：
  - `checkForUpdates`：后端失败 → `updateManager.checkLatestRelease()` + `compareVersions` 构造同构结果；结果透传 `sha256/size`。
  - silent 发现新版本：发 `update-available` 事件 + `showNotification('发现新版本', ...)` 系统通知。
  - `download-and-apply-update`：兼容字符串/对象 payload `{downloadUrl, sha256}`，ZIP 与 EXE 路径都走 `downloadUpdateWithFallback`，进度文案显示源名。
- `settings.js`：记录 `updateDownloadSha256`，调用改为传对象。

### 3. 后端接口加固（fp-003）

- `UpdateController.java`：
  - Jackson `ObjectMapper.readValue(body, Map.class)` 替换手工字符串解析。
  - `ConcurrentHashMap<String, CacheEntry>` + 10 分钟 TTL（`isFresh`）。
  - `GH_TOKEN`/`GITHUB_TOKEN` 环境变量 → `Authorization: Bearer`。
  - `findUpdateAsset`：优先级 clip-update ZIP > CutShelter ZIP > CutShelter EXE，提取 `digest`（`sha256:` 前缀剥离）与 `size`；响应新增 `sha256`/`size`。

### 4. 发布脚本（fp-004）

- `release.bat` / `release.sh`（9 步）：
  - Step 2 版本号确认：读取当前版本，`set /p`/`read -p` 询问「是否递增版本号并更新 package.json？(y/N)」；y → 建议下一 patch（x.y.(z+1)）并输入校验 `^\d+\.\d+\.\d+$`；N → 沿用当前版本并检测 `gh release view vX` 已存在时确认覆盖。
  - Step 3 仅当版本变化时写 package.json + `chore: bump version` 提交。
  - Step 7 统一 `node scripts\build-update-zip.js`（替代内联 PowerShell 压缩）。
  - Step 9 `gh release create` 附带 `%DIST_DIR%\*.zip` + `*.sha256`。

## 接口定义

- `GET /api/update/check?currentVersion=x.y.z`
  - 响应：`{ hasUpdate, latestVersion, currentVersion, releaseNotes, releaseUrl, downloadUrl, sha256, size, message }`
  - `sha256`：GitHub asset `digest` 剥离 `sha256:` 前缀；无则缺省。
- IPC `download-and-apply-update`：payload `{ downloadUrl, sha256 }`（兼容旧字符串）。
- `update-config.json`：`{ autoUpdate, frequency, lastCheck, mirrorUrls? }`（mirrorUrls 可选，手配镜像前缀数组）。

## 关键决策

1. **不做 Gitee 分发**（用户决策）：GitHub 权威源 + gh-proxy 镜像兜底；Gitee 仅记录为备选。
2. **TODO 目录保留**（用户决策）：产品概览 JSON 随安装包与更新包分发。
3. **不引入 electron-updater 框架**：现有自定义流程可维护，改动面小；文档记录为未来选项。
4. **检查统一走后端 + 缓存**，客户端直连仅降级：减少 GitHub API 调用与速率限制影响。
5. **镜像前缀可配置**：默认内置三个公共实例，`mirrorUrls` 允许覆盖，避免实例失效后无法自救。
6. **打包脚本版本号交互默认不强制递增**：y/N 由用户决定，CI 无输入时默认沿用当前版本。
