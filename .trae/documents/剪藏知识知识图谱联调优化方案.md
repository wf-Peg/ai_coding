# 剪藏 → 知识 → 知识图谱 联调优化方案

## 一、摘要（Summary）

本次方案解决三个核心问题：

1. **「来源剪藏 / 关联知识」交互与核心逻辑**：目前剪藏↔知识仅靠 `Knowledge.sourceClipIds` 单向反链，缺少统一、可查询、可双向回指的关联载体；剪藏侧无任何知识回指针。
2. **知识整理核心逻辑薄弱**：`KnowledgeService.synthesizeKnowledge(List)` 是返回 null 的 TODO 桩；收件箱整理只产出 Markdown 日报、不生成 Knowledge 模型；剪藏→知识的多步流转（勾选→合成→跳转编辑→保存）割裂。
3. **知识图谱只连知识之间，未打通剪藏数据**：后端 `ContentRelation`/`RelationIndexService`/`relation-index.json` 是**完整但从未接线的死代码**；图谱前端 `knowledge-graph.js` 只调 `GET /api/knowledge/list`，仅用 `linkedKnowledgeIds` 建边，节点类型只有 knowledge。

**核心设计思路**：激活既有（死代码化的）统一关系索引 `RelationIndexService`，把「剪藏→知识（derived_from）、知识→知识（linked_to）」统一写成带类型的 relation，新增 `GET /api/graph` 端点为图谱提供「节点（四大类型）+ 边（全部 relation）」的数据源；前端图谱改为消费该端点，从而把剪藏数据真正纳入图谱。同时补强知识整理的 provenance（来源元数据）与一键「整理+合成」流水线。

不引入新框架、不引入数据库，沿用「本地 JSON 文件 + 现有 service/controller 分层」的既有约束。

## 二、现状分析（Current State Analysis）

所有结论均来自对代码的只读调研，引用具体文件。

### 2.1 存储与数据模型
- 无数据库，全部 JSON 文件（`agent.md` 明确约束）。`FileStorageService` 为唯一持久层，根路径由 `application.yml` 的 `clip.storage.path` 指向外置 `Clip_Bed\clip-storage`。
- 剪藏：`{分类目录}/{yyMMdd}.json`；知识：`knowledge-base/{yyyy-MM-dd}.json`。
- `model/Knowledge.java`：含 `sourceClipIds`(L43)、`linkedKnowledgeIds`(L49)，是当前唯一 clip↔knowledge 关联载体。
- `model/ClipContent.java`：**无**任何知识回指字段（无 `knowledgeIds`）。
- `model/KnowledgeEntry.java`：遗留死模型，无任何 Controller 暴露端点，仅 `ContentIndexService` 读它建节点。

### 2.2 clip↔knowledge 当前关联机制
- 唯一机制是 `Knowledge.sourceClipIds`（单向反链）。反查靠 `KnowledgeService.getKnowledgeByClipId`(L180-185) 全量扫描 JSON。
- 剪藏→知识真实路径仅一个：`POST /api/knowledge/from-clip/{clipId}`（`KnowledgeService.createFromClip` L197-226）。
- `POST /api/knowledge/synthesize`（Controller L240-290）只返回 AI 草稿，**不落库**；service 层同名方法 `synthesizeKnowledge(List)`(L237-241)**是 TODO 占位返回 null**。
- 收件箱整理（`ClipService.organizeInbox`）与知识库日报（`ContentOrganizeService.organizeContent`）都**不**创建 Knowledge 记录。

### 2.3 知识图谱现状
- 后端 `index/ContentRelation.java`（record，含 fromId/toId/relationType/source/confidence/createdAt）与 `index/RelationIndexService.java`（add/remove/findFor/readAll，原子写）**定义完整**，但生产代码无任何 `new RelationIndexService` 调用 → `relation-index.json` 运行时永不写入，是**死代码脚手架**。
- 运行时只生成节点索引 `content-index.json`（`ContentIndexService`，含 clip/knowledge/todo/learning-plan 四类 `ContentRef` 节点），由 `ContentIndexAutoSyncService` 每 5 分钟重建。
- 前端 `knowledge-graph.js`：`fetchData()`(L25) 只调 `GET /api/knowledge/list`；`buildGraph`(L42) 节点仅 knowledge、边仅由 `linkedKnowledgeIds` 双向生成；无搜索、无聚类、无跨类型节点。

### 2.4 前端交互现状
- `clip.html`：已有「创建知识条目」（L4296-4320/`createKnowledgeFromClip`）与批量「合成知识」（L5475-5516/`synthesizeKnowledge`），经 sessionStorage + `navigateKnowledgeCreate` 消息跳转知识编辑器；详情区已有「已关联知识」反查展示（`renderLinkedKnowledge` L5531-5573 调 `GET /api/knowledge/by-clip/{clipId}`）。
- `knowledge-detail.html/js`：已有「来源剪藏」区（`renderSourceClips` L91-125）+「关联知识」区（`renderLinkedKnowledge` L183-223）。
- `knowledge-editor.html/js`：已有来源剪藏管理（`sourceClipIds` chips + 添加来源弹窗）。

**结论**：交互骨架已存在，但数据层关联是「单向反链 + 反向全量扫描」，图谱与剪藏完全脱节，知识整理合成逻辑残缺。

## 四、目标设计（Proposed Design & Changes）

### 设计总览（数据流转图）

```
剪藏(clip) ──derived_from──▶ 知识(knowledge) ──linked_to──▶ 知识(knowledge)
   │  sourceClipIds(权威)          │  linkedKnowledgeIds(权威)
   └────────────┴──────────────────┘
                ▼
   Unified Relation Store (relation-index.json)
                │  add() 在创建/链接时写入 typed relation
                ▼
   GET /api/graph  ──▶  knowledge-graph.js 渲染「剪藏节点 + 知识节点 + 边」
```

**设计原则**：以「统一关系索引」为图谱数据脊梁；`sourceClipIds` / `linkedKnowledgeIds` 保留为 JSON 字段上的**权威来源**，relation-index 是其**可查询的投影**，二者通过同步保持一致性。这样既不改动既有数据模型，又能让图谱读到剪藏节点与跨类型边。

---

### P1（后端核心）：接线统一关系索引 + 新增 Graph 端点

**文件**：
- `backend/src/main/java/com/example/clip/service/KnowledgeService.java`
- `backend/src/main/java/com/example/clip/service/GraphService.java`（新建）
- `backend/src/main/java/com/example/clip/controller/GraphController.java`（新建）
- `backend/src/main/java/com/example/clip/config/AppConfig.java`（如有注入线索）

**做**：
1. 在 `KnowledgeService` 中注入 `RelationIndexService`（指向 `index/relation-index.json`），在以下时机写入 typed relation：
   - `createFromClip`：写 `clip:{id} ──derived_from──▶ knowledge:{id}`（source=`clip_to_knowledge`）
   - `saveKnowledge` / wikilink 解析（`manageBidirectionalLinks`）：对每个 `linkedKnowledgeIds` 写 `knowledge:{a} ──linked_to──▶ knowledge:{b}`
   - `synthesizeKnowledge` 落库成功时：对每个来源 clip 写 `derived_from`
2. 提供关系一致性：`FileStorageService` 或 `ContentIndexAutoSyncService` 中增加一次「从 JSON 权威字段重建 relation-index」的幂等同步（无需全量重构，仅作兜底）。
3. 新增 `GET /api/graph`（`GraphService` + `GraphController`）：
   - 节点：读 `content-index.json`（clip + knowledge，可选 todo / learning-plan 开关）
   - 边：读 `relation-index.json`，若为空则回退从 `sourceClipIds`+`linkedKnowledgeIds` 派生
   - 返回 `{ nodes:[{id,type,title,summary,category,tags,linkedCount}], links:[{source,target,type}] }`

### P2（后端核心）：知识整理核心逻辑补强

**文件**：
- `KnowledgeService.java`
- `dto/KnowledgeRequest.java` / `dto/KnowledgeResponse.java`（扩展字段）

**做**：
1. 实现 `KnowledgeService.synthesizeKnowledge(List<Long>)`：把 Controller 现有 AI 合成逻辑收敛进 service，返回可保存的知识对象（含 `sourceClipIds`、provenance），并支持 `persist` 参数（合成即保存 vs 仅草稿）。
2. **provenance 增强**：`createFromClip`/`synthesize` 时把来源剪藏的 `sourceUrl`、`siteName`、`capturedAt` 一并写入 Knowledge（新增字段如 `sourceRefs: [{clipId, sourceUrl, siteName}]`），让知识详情能展示更丰富的「来源」。
3. 保持 `manageBidirectionalLinks` 的 wikilink 逻辑，同时把产生的边写入 relation-index。

### P3（前端）：图谱打通剪藏数据 + 交互增强

**文件**：
- `frontend/knowledge-graph.html`
- `frontend/knowledge-graph.js`

**做**：
1. `fetchData()` 改为调 `GET /api/graph`；`buildGraph` 支持多类型节点：
   - 剪藏节点用不同形状/颜色（如方形/橙系）、知识节点圆形/蓝系；
   - 边按 `type` 区分样式（`derived_from` 虚线、`linked_to` 实线），hover 显示边类型提示。
2. 增加**搜索框**（按 title/tags 过滤）与**按 category 聚类**（`d3.forceX/forceY` 按分类分组，或分级色彩）。
3. 侧栏点击：剪藏节点链接到 `clip.html`，知识节点链接到 `knowledge-detail.html`。
4. 提供「仅知识 / 剪藏+知识」视图切换开关（默认剪藏+知识）。
5. 新增关系一致性说明/刷新按钮（调 `POST /api/relations/sync` 重建 relation-index）。

### P4（前端 UX）：来源剪藏 / 关联知识体验优化

**文件**：
- `frontend/clip.html`
- `frontend/knowledge-detail.html` / `knowledge-detail.js`
- `frontend/knowledge-editor.html` / `knowledge-editor.js`

**做**：
1. `clip.html`：剪藏列表项增加「已关联知识」角标（反查 `GET /api/knowledge/by-clip/{id}` 已在详情区存在，提升到列表维度）；「合成知识」按钮在勾选含「已关联」剪藏时给出提示。
2. `knowledge-detail.js`：来源剪藏区展示来源 URL/站点名；点击来源剪藏改为**内联弹窗预览**（呼应知识库与Vault模块 R-001 已修方案），并提供「去剪藏 / 在编辑器打开」入口。
3. `knowledge-editor.js`：来源剪藏 chips 显示来源站点名；保存时若来源剪藏已关联别条知识给出提示。

## 六、假设与决策（Assumptions & Decisions）

| 决策 | 结论 | 理由 |
|------|------|------|
| D1 关联载体 | 保留 `sourceClipIds`/`linkedKnowledgeIds` 为权威，relation-index 为其投影 | 不改既有数据模型、风险最低 |
| D2 图谱节点范围 | 默认「剪藏 + 知识」；todo/learning-plan 作为可开关 | 聚焦用户诉求（两块数据），避免范围膨胀 |
| D3 图谱数据源 | 统一走 `GET /api/graph`，前端不再各端各自拼边 | 单一真源，避免前端重复逻辑 |
| D4 合成行为 | `synthesizeKnowledge` 支持「合成即保存」与「仅草稿」参数 | 兼顾现有「草稿跳转编辑」与「一键整理」两种语义 |
| D5 关系同步 | 创建/链接时写 + 兜底全量重建（幂等） | 保证一致性与容错 |
| D6 KnowledgeEntry | **保留**（作为轻量知识卡片层，补齐端点后续用），本轮不改 | 降低改动面；若确认无用可另立删除任务 |
| D7 范围 | 本轮**不**做 Obsidian/Media 层联调（属图片功能设计范畴），仅聚焦关联与图谱 | 保持方案聚焦 |
