# 剪藏「问我的剪藏库」修复 + 流式输出设计

## 一、背景与目标

用户反馈剪藏模块「问我的剪藏库」两个问题：

1. **报错**：提问后返回 `AI 服务暂时不可用，问题已保留，请稍后重试。`，但 AI 服务与 API Key 实际可用。
2. **体验**：等待很久后一次性输出全部结果，无中间反馈。

目标：修复错误根因 + 将全库问答改为 SSE 流式输出，回答边生成边展示，来源条目先于回答渲染作为进度反馈。

## 二、根因分析（已排查确认，日志佐证）

错误链路：

1. [PromptConfigService.java](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/backend/src/main/java/com/example/clip/service/PromptConfigService.java#L46-L76) 的 `getPromptConfig()` 对 20+ 个 Prompt 字段做了默认值归一化，**唯独没有归一化 `clipAskSynthesisPrompt`**；`getDefaultConfig()`（L276-299）与 `savePromptConfig()`（L83-112）同样遗漏。
2. 磁盘上已存在的旧配置 JSON 无该字段 → `loaded.getClipAskSynthesisPrompt()` 为 null → 归一化结果仍为 null。
3. [AiService.java](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/backend/src/main/java/com/example/clip/core/AiService.java#L1057-L1075) `answerClipQuestion()` 取到 null 的 systemPrompt。
4. `OpenAiCompatibleLlmProvider.chat()` 用 `Map.of("role","system","content",systemPrompt)` 构造消息，null 触发 NPE（日志确认：`[custom] chat failed: null` → `java.lang.NullPointerException` → `Map.of`）。
5. `RoutingLlmProvider` 降级到 DeepSeek（同 NPE）/DashScope（免费额度耗尽）均失败 → 返回 null → [ClipController.java](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/backend/src/main/java/com/example/clip/controller/ClipController.java#L575-L581) 输出错误文案。

默认 prompt 常量 `DEFAULT_CLIP_ASK_SYNTHESIS_PROMPT` 已存在于 [PromptConfigService.java](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/backend/src/main/java/com/example/clip/service/PromptConfigService.java#L689-L698)，只是从未被装配。

## 三、改动方案

### 后端 1：PromptConfigService.java — 补齐 clipAskSynthesisPrompt 归一化

在 3 处补一行（常量已存在，直接引用）：

- `getPromptConfig()` L75 之后追加：
  ```java
  normalized.setClipAskSynthesisPrompt(normalizeOrDefault(loaded.getClipAskSynthesisPrompt(), DEFAULT_CLIP_ASK_SYNTHESIS_PROMPT));
  ```
- `getDefaultConfig()` L297 之后追加：
  ```java
  c.setClipAskSynthesisPrompt(DEFAULT_CLIP_ASK_SYNTHESIS_PROMPT);
  ```
- `savePromptConfig()` L108 之前追加：
  ```java
  normalized.setClipAskSynthesisPrompt(normalizeOrDefault(config.getClipAskSynthesisPrompt(), existing.getClipAskSynthesisPrompt()));
  ```

### 后端 2：AiService.java — 新增流式问答方法

在 `answerClipQuestion()` 旁新增（复用同样的消息构造逻辑，改调 `streamChat`）：

```java
public ChatStreamHandle streamClipAnswer(String question, Map<String, String> pageContents, ChatStreamListener listener) {
    String systemPrompt = promptConfigService.getClipAskSynthesisPrompt();
    // 与 answerClipQuestion 相同的 userMessage 拼装（Question + 编号片段）
    List<ChatMessage> messages = List.of(
            new ChatMessage("system", systemPrompt),
            new ChatMessage("user", userMessage.toString()));
    return llmProvider.streamChat(messages, listener);
}
```

说明：按用户确认使用**默认模型**（与编辑器 AI 对话 `AiChatController` 同路径），不新增 tier 流式管线。异常时直接调用 `listener.onError`，由控制器处理。需确认 `AiService` 已注入 `LlmProvider`（已有 `llmProvider` 字段）。

### 后端 3：ClipController.java — 新增 SSE 端点 `POST /api/clip/ask/stream`

参照 [AiChatController.java](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/backend/src/main/java/com/example/clip/controller/AiChatController.java) 的 SseEmitter + 心跳模式（紧凑版，不重构 AiChatController）：

1. **抽取私有方法** `buildAskContext(String question)`：把现有 `/ask` L530-572 的「检索 + 截断 + 拼装 pageContents/sources」逻辑抽出来，`/ask` 与新端点共用（行为不变，消除 ~30 行重复）。
2. **新端点流程**：
   - 校验 question 非空、截断 200 字（同 `/ask`）。
   - 创建 `SseEmitter(120_000L)`，注册 `onCompletion/onTimeout/onError`，15s 心跳。
   - `CompletableFuture.runAsync` 内：
     - `buildAskContext` 无候选 → 发 `status` 事件 `{"status":"no_results","answer":"库里没有找到..."}` → 关闭。
     - 有候选 → 先发 `sources` 事件 `{"sources":[...]}`（前端先渲染来源做进度反馈）→ 调用 `aiService.streamClipAnswer(...)`，listener 中：
       - `onDelta` → `send("delta", {"content": ...})`
       - `onComplete` → `send("done", {})` + 关闭
       - `onError` → `send("error", {"message": ...})` + 关闭
3. **事件协议**（与前端约定）：
   - `status`（no_results 时，含 answer 文案）
   - `sources`（含 sources 数组，结构同现有 `/ask` 返回）
   - `delta`（含 content 增量）
   - `done`（结束）
   - `error`（含 message）
   - `heartbeat`（前端忽略）
4. 新增 import：`SseEmitter`、`ChatMessage`、`ChatStreamHandle`、`ChatStreamListener`、`CompletableFuture`、`Executors`、`ScheduledExecutorService`、`ScheduledFuture`、`TimeUnit`、`AtomicBoolean`、`IOException`。

### 后端 4：electron/main.js — 代理豁免 SSE

[main.js](file:///l:/归档/30_Projects%20(行动项目)/31_Work%20(主要工作)/code/ai_coding/electron/main.js#L1749-L1765) 的代理逻辑中，将 `/api/clip/ask/stream` 加入豁免：

- `const isClipAskStream = urlPath.startsWith('/api/clip/ask/stream');`
- `const noTimeout = isAiStream || isWikiQuery || isWikiLint || isClipAskStream;`
- cache-control / keep-alive 分支条件 `if (isAiStream || isClipAskStream)`。

否则代理 30s 超时会掐断流。

### 前端 5：clip-list.js — submitAskQuestion 改为消费 SSE

`clip.html` 未加载 `editor-ai-chat-core.js`（已确认），故在 `clip-list.js` 内加一个 ~40 行局部 `SseParser`（与 `EditorAiChatCore.SseParser` 相同的行解析逻辑），不引入新依赖。

重写 `submitAskQuestion()`：

1. 局部变量：`answerBuf`、`abortController`（模块级，供 `closeAskModal()` 中止）。
2. `fetch(`${API_BASE_URL}/ask/stream`)`，headers 含 `Accept: text/event-stream`，`signal` 传 controller。
3. `response.body.getReader()` + `TextDecoder` + `SseParser` 消费事件：
   - `sources` → 立即渲染来源清单（复用现有 L1030-1050 的 HTML 拼接逻辑），显示「正在组织回答…」占位。
   - `delta` → `answerBuf += content`，**120ms 防抖**调用 `MediaKit.render.renderMarkdown(answerBuf)` 增量渲染到 `#ask-answer-body`。
   - `status`（no_results）→ 显示返回文案。
   - `done` → 最终渲染一次，恢复按钮。
   - `error` → 显示「AI 服务暂时不可用，请稍后重试」，恢复按钮。
   - `heartbeat` → 忽略。
4. `closeAskModal()` 增加 `abortController?.abort()`，并重置按钮状态。
5. 保留现有 `openAskModal()`、DOM 结构与按钮禁用/文案逻辑（「思考中…」）。

旧 `/ask` 端点保留不动（兼容/回退），前端切换用 `/ask/stream`。

## 四、假设与决策

- 流式使用各 provider **默认模型**（用户已确认），与编辑器 AI 对话一致；回答质量与档位强模型的差异暂不处理。
- 不新增 tier 流式管线、不重构 `AiChatController`，降低回归风险。
- 前端不引入新库；SSE 解析器局部实现。
- 「问题已保留」文案本身没有服务端持久化，本次不新增该能力，仅修复报错与流式体验。
