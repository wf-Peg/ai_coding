# 剪藏列表加载优化：批量关联接口 + 前端缓存

## 背景（Context）

剪藏列表（frontend 剪藏页）加载慢，根因是 N+1 请求问题：`renderClipList` 渲染每条剪藏后立即发起两个独立 HTTP 请求——关联知识（`GET /api/knowledge/by-clip/{id}`）与计划反链（`GET /api/learning-plan/by-clip/{id}`），一页 50 条 = **100 个并发请求**，且后端每个单条请求都做一次全量扫描（`getKnowledgeByClipId`/`getPlansByClip` 均为遍历全量数据后过滤），性能极差。

目标：**每页从 100+ 请求降为 2 个批量请求**，展开/加载更多/恢复展开态不再重复请求（读缓存），并保持现有交互（角标、反链、加载更多）不变。

**本期范围**：仅做批量接口 + 前端缓存（P0-1）。后端列表接口真分页（`page/size` 服务端化）改动面大、收益边际，**本期不做**，作为后续可选优化。

public Map<Long, List<Knowledge>> getKnowledgeByClipIds(List<Long> clipIds) {
    Map<Long, List<Knowledge>> result = new HashMap<>();
    if (clipIds == null || clipIds.isEmpty()) return result;
    Set<Long> idSet = new HashSet<>(clipIds);
    for (Knowledge k : storageService.getAllKnowledge()) {
        if (k.getSourceClipIds() == null) continue;
        for (Long cid : k.getSourceClipIds()) {
            if (idSet.contains(cid)) {
                result.computeIfAbsent(cid, x -> new ArrayList<>()).add(k);
            }
        }
    }
    return result;
}

#### 2. LearningPlanService + LearningPlanController

`LearningPlanService` 新增 `getPlansByClipIds`：复用 `collectPlanRefs` 的 planRef 组装结构（planId/planTitle/phases），改为一次遍历 `getAllLearningPlans()`，按 phase 的 `sourceClipIds` 命中 `idSet` 时按 clipId 分组；**同一计划的多个命中阶段合并进同一个 planRef 的 `phases` 数组**（与单条接口 `collectPlanRefs` 行为完全一致，避免列表出现重复计划行）：

```java
public Map<Long, List<Map<String, Object>>> getPlansByClipIds(List<Long> clipIds) {
    Map<Long, List<Map<String, Object>>> result = new HashMap<>();
    if (clipIds == null || clipIds.isEmpty()) return result;
    Set<Long> idSet = new HashSet<>(clipIds);
    // clipId -> planId -> planRef（合并同计划多阶段）
    Map<Long, Map<Long, Map<String, Object>>> planRefsByClip = new HashMap<>();
    for (LearningPlan plan : fileStorageService.getAllLearningPlans()) {
        if (plan.getId() == null) continue;
        for (Phase phase : plan.getPhases()) {
            if (phase.getSourceClipIds() == null) continue;
            for (Long cid : phase.getSourceClipIds()) {
                if (!idSet.contains(cid)) continue;
                Map<Long, Map<String, Object>> byPlan =
                        planRefsByClip.computeIfAbsent(cid, x -> new LinkedHashMap<>());
                Map<String, Object> planRef = byPlan.computeIfAbsent(plan.getId(), x -> {
                    Map<String, Object> ref = new LinkedHashMap<>();
                    ref.put("planId", plan.getId());
                    ref.put("planTitle", plan.getTitle());
                    ref.put("phases", new ArrayList<Map<String, Object>>());
                    return ref;
                });
                Map<String, Object> phaseRef = new LinkedHashMap<>();
                phaseRef.put("phaseNumber", phase.getPhaseNumber());
                phaseRef.put("phaseTitle", phase.getTitle());
                @SuppressWarnings("unchecked")
                List<Map<String, Object>> phases = (List<Map<String, Object>>) planRef.get("phases");
                phases.add(phaseRef);
            }
        }
    }
    planRefsByClip.forEach((cid, byPlan) -> result.put(cid, new ArrayList<>(byPlan.values())));
    return result;
}
```

> 与单条接口 `collectPlanRefs` 的输出结构完全一致：每条 planRef 含 planId/planTitle/phases（同计划多阶段合并），前端展示无差异。

### 前端：缓存 + 批量预取（clip-sync.js + clip-list.js）

#### 3. clip-sync.js 顶部新增缓存与批量函数

在 `renderLinkedKnowledge` 前（文件顶部的全局 `var` 区域）新增：

```js
// ====== 关联数据批量缓存（N+1 → 每页 2 个批量请求）======
var linkedKnowledgeCache = new Map(); // clipId(String) -> knowledgeList
var planBacklinksCache = new Map();   // clipId(String) -> plans

async function batchLoadClipRelations(clipIds) {
    const ids = [...new Set((clipIds || []).filter(id => id != null).map(String))];
    if (ids.length === 0) return;
    const missingLinked = ids.filter(id => !linkedKnowledgeCache.has(id));
    const missingPlans = ids.filter(id => !planBacklinksCache.has(id));
    if (missingLinked.length > 0) {
        try {
            const res = await axios.get(`${KNOWLEDGE_API_BASE_URL}/by-clips`,
                { params: { clipIds: missingLinked.join(',') } });
            Object.entries(res.data || {}).forEach(([id, list]) =>
                linkedKnowledgeCache.set(String(id), list || []));
        } catch (e) { console.error('批量获取关联知识失败:', e); }
    }
    if (missingPlans.length > 0) {
        try {
            const res = await axios.get(`${API_ROOT}/learning-plan/by-clips`,
                { params: { clipIds: missingPlans.join(',') } });
            Object.entries(res.data || {}).forEach(([id, list]) =>
                planBacklinksCache.set(String(id), list || []));
        } catch (e) { console.error('批量获取学习计划反链失败:', e); }
    }
}
```

#### 4. `renderLinkedKnowledge` / `renderPlanBacklinks` 改为缓存驱动

两函数开头改为「先读缓存，未命中才单条请求并回填缓存」，渲染逻辑保持不变：

```js
async function renderLinkedKnowledge(clipId) {
    const listEl = document.getElementById(`linkedKnowledgeList-${clipId}`);
    const noDataEl = document.getElementById(`noLinkedKnowledge-${clipId}`);
    if (!listEl || !noDataEl) return;
    const key = String(clipId);
    let knowledgeList = null;
    if (linkedKnowledgeCache.has(key)) {
        knowledgeList = linkedKnowledgeCache.get(key);
    } else {
        try {
            const response = await axios.get(`${KNOWLEDGE_API_BASE_URL}/by-clip/${clipId}`);
            knowledgeList = response.data || [];
            linkedKnowledgeCache.set(key, knowledgeList);
        } catch (error) {
            // 保留现有错误处理（隐藏列表、显示空态）
            console.error('获取已关联知识失败:', error);
            listEl.style.display = 'none';
            noDataEl.style.display = 'block';
            return;
        }
    }
    // …以下渲染角标/列表逻辑保持不变…
}
```

`renderPlanBacklinks` 同样处理（`planBacklinksCache` + 单条兜底）。

#### 5. `renderClipList` 批量预取（clip-list.js L221-230）

先渲染条目，再批量预取，完成后统一渲染角标/反链 + 恢复展开态（展开恢复必须在缓存填充之后执行，否则回退单条请求；原「展开态恢复」同步块整体移入 `.finally()`）：

```js
const shown = clips.slice(0, visibleClipCount);
shown.forEach(clip => {
    if (clip && clip.id != null) {
        clipCache.set(String(clip.id), clip);
    }
    const clipItem = createClipItem(clip, false);
    clipItemsContainer.appendChild(clipItem);

// 批量预取关联数据（2 个请求替代 N×2），完成后由缓存驱动渲染
const shownIds = shown.filter(c => c && c.id != null).map(c => c.id);
batchLoadClipRelations(shownIds).finally(() => {
    shown.forEach(clip => {
        if (clip && clip.id != null) {
            renderLinkedKnowledge(clip.id);
            renderPlanBacklinks(clip.id);
        }
    });
    // 恢复之前展开的剪藏详情（缓存已填充，零新增请求）
    expandedIds.forEach(id => {
        const detail = document.querySelector(`.clip-detail[data-clip-id="${id}"]`);
        if (detail) {
            detail.classList.add('expanded');
            detail.querySelectorAll('.content-text.truncated').forEach(el => el.classList.add('expanded'));
            const btn = detail.closest('.clip-item')?.querySelector(`.expand-btn[data-clip-id="${id}"]`);
            if (btn) {
                btn.classList.add('expanded');
                const text = btn.querySelector('.text');

            renderPlanBacklinks(parseInt(id));
        }
    });
});
```

- `batchLoadClipRelations` 内部已 try/catch，`.finally()` 后渲染函数走缓存（批量失败时回退单条），无未处理 Promise。
- 「加载更多」再次进入 `renderClipList`：已缓存的第一页命中，仅新页 id 发起 2 个批量请求（`missing*` 过滤）。
- `toggleDetail` 展开（L653-655）仍调用同一对函数 → 读缓存，零新增请求；展开态恢复改在 `.finally()` 中执行，保证首次/轮询刷新时同样命中缓存。
- 原 `renderClipList` 中的「恢复展开态」同步代码块（原 L245-260）删除，逻辑上移到 `.finally()` 回调。

## 假设与决策（Assumptions & Decisions）

- **本期不做后端真分页**：列表接口仍返回全量（个人应用数据量级下 JSON 传输不是瓶颈），仅修复 N+1（瓶颈主因）。后续如需再评估 `page/size`。
- **批量响应结构**：`Map<clipId, List<...>>`，且按键顺序 = 请求 clipIds 顺序（`LinkedHashMap`），前端按自身 `shownIds` 取用。
- **缓存按字符串 clipId 存**（`String(id)`），与 DOM `id` 拼接方式一致；空数组视为有效缓存（区分「已查为空」与「未查询」）。
- **前端继续用 axios 直连风格**（clip-sync.js 现状），不强行迁移到 `window.apiClient`（`apiClient` 无批量关系方法，且两处风格已并存）。
- **批量失败自动降级**：批量请求失败不影响列表渲染，渲染函数回退单条请求（与现状行为一致）。
- **扩展版不涉及**：browser-extension 无此 N+1 逻辑。
