# 应用启动速度优化：窗口先出 + 后台加载

## Summary

目标：让主窗口 **立即显示（~1s 内）**，把后端、索引、右键菜单、缓存清理都移到后台异步执行，兼容 `full / frontend-only / frontend-async-backend` 三种启动模式。核心优化四处：

1. **右键菜单注册 -> 异步 + 延后**：现为每次启动在 `createMainWindow` 前执行 `~120 次` 同步 `spawnSync('reg',…)`，是最主要的**非后端**首屏阻塞（数秒）。
2. **本地索引初始化 -> 增量 + 变更门控**：现为每次启动同步 `clearAll + 全量重建`，需读取解析每个 clip 文件，大库可达数秒。
3. **clearCache -> 不卡首屏**：现 `await …Promise.race(clearCache, 8s)` 在最前面，个别机器卡满 8 秒才出窗。
4. **后端启动不再卡建窗**：现 `full` 模式 `await startBackend`（JVM+Spring 十几秒）后才建窗；改为先建窗、后端后台启动（三种模式统一「立即出窗」）。

## Proposed Changes

### Change 1 — 右键菜单注册：改异步 + 延后到出窗后（dominant 非后端收益）

**文件**：`electron/context-menu-registry.js`、`electron/main.js`

- `context-menu-registry.js`：
  - 把 `runReg(args, silent)` 由 `spawnSync` 改为**异步** `execFile('reg', args)` 的 Promise 化封装。保留参数数组方式（避免引号/中文路径编码问题），保留 `windowsHide:true`、`timeout`。
  - 相应把 `registerContextMenu / registerWindowsContextMenu / registerFlatItem / registerOpenWith / unregisterWindowsContextMenu / unregisterOpenWith` 改为 `async`；内部 `await runReg(...)`，逻辑不变。
  - 保持按序执行，使主进程**不再阻塞**（reg add/delete 各自独立、顺序无必然依赖，失败静默处理逻辑保留）。
- `main.js`：
  - `ensureContextMenuRegistered(config)` 改为 `async`（await `registerContextMenu`），调用点**不再阻塞**：
    - 正常启动（原 L5031-5032）：从 `createMainWindow` 之前的同步位置，移到 `createMainWindow` 之后，用 `setTimeout(500)` 延后触发，且不 `await`（fire-and-forget）。
    - 首次运行 config-done（原 L4950）：同样延后、不 await。
- 收益：去掉启动同步 `~120` 次 `spawnSync`，主进程不再冻结卡住。

### Change 2 — 本地索引：增量 + 变更门控（避免每次启动全量重建）

**文件**：`electron/sqlite/scanner.js`、`electron/sqlite/index-service.js`

- `scanner.js` 新增 `getStorageSignature(clipStoragePath)`：仅做目录遍历 + `statSync` 取每个 clip 文件的 `mtimeMs`（**不读取文件内容、不 JSON.parse**），返回轻量签名（文件数 + max(mtime)）。成本 = 一次 readdir 树遍历，远低于现状的内容全读。
- `index-service.js` 的 `initLocalIndex`：
  - 打开库后取 meta `index_signature`；若满足 `generation>0 且 signature 相同且 FTS 已建` → **跳过全量重建**，直接返回现有 `status()`（保留 generation，近乎 O(1) 冷启动）。
  - 否则执行现有全量重建逻辑，完成后写入 `index_signature` 与 `data_generation+1`。
- 运行时仍由现有 watcher/rescan 维护增量（本方案不改 `rescan`）。
- 收益：未变更的冷启动不再读文件内容/重建索引，索引启动成本趋近于 0；数据有改动时行为与现状一致（读到的一次性成本可接受，且已延后台）。

### Change 3 — clearCache 不再卡首屏

**文件**：`electron/main.js`（whenReady L4804-4820）

- 保留 8s 超时降级与 try/catch（防内网崩溃），但**不作为首屏前置 await**：
  - 改为 `const p = clearCacheWithTimeout(); p.catch(()=>{});` 不 `await`，让后续（createTray/config/建窗）立即执行。
  - 或将其下沉到 `createMainWindow` 之后、与其它后台任务并行执行。
- 收益：个别机器 clearCache 挂起时不再推迟出窗。

### Change 4 — 后端启动移到建窗后（三种模式统一「立即出窗」）

**文件**：`electron/main.js`（正常启动分支 L5026-5101）

- 重组顺序为：
  1. `syncModelConfigJson(config)`（快，保留）
  2. `createMainWindow(config)`（**最先建窗**）
  3. `startFrontendServer(config)`（快，启动静态服务；窗口 `loadWithRetry` 已带 2s 重试，偶发未就绪会自动重载）
  4. 按 `config.startupMode` 触发后端（`full`/`frontend-async-backend` 均**后台**启动，不再 await 建窗；`frontend-only` 不启动）：
     - 复用现有 `startBackend(config).then(...)` 进度推送、`backend-ready` 通知、`startReminderScheduler`、`initExceptionLogger` 逻辑，仅从「await 后建窗」改为「建窗后异步 then」。
     - `full` 模式不再 `await`（窗口不再被 JVM 卡住；后端就绪通知仍会推送到界面）。
  5. `ensureContextMenuRegistered(config)` 延后触发（见 Change 1）、本地索引已在 whenReady 侧完成初始化（见 Change 2，已变增量/近 O(1)）。
- 首次运行（config 未 configured）保持现有引导流程，但 `ensureContextMenuRegistered` 同样改异步延后（Change 1）；`createMainWindow` 时机保持等待后端就绪以维持引导体验。
- 兼容性：不改变各模式的「是否自动启动后端」语义，只解除「后端就绪才出窗」的耦合。

## Assumptions & Decisions

- 用户确认接受「立即出窗 + 后台加载」。`full` 模式窗口不再等后端，后端仍自动拉起重用，就绪后仍推送进度/通知。
- 索引「未变更则跳过重建」依赖 watcher 在运行时维护增量；若 watcher 不可用，FTS/增量可能滞后，但索引本身是缓存、可从权威 JSON 重建，属可接受降级。
- 右键菜单异步化：注册按序 `execFile` 非阻塞，失败静默策略不变；极端情况下注册尚未完成即用户右键，菜单短暂缺失，下次进入稍后补上——adoptable（烧录式注册仍保证一致性）。
- 首次运行流程不做「先出窗不等后端」的大改造（保持引导体验），仅顺带异步化右键菜单。
