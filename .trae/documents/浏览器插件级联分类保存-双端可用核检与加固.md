# 浏览器插件级联分类保存：双端可用核检与加固

## 摘要
对上一轮「浏览器插件保存剪藏报错修复」的改动做双端（桌面端 + 浏览器插件端）可用性核检，
重点验证 **级联（二级分类）条件下** 的剪藏保存。核检结论：两端共享同一套后端 REST API
（`POST /api/clip/add`），payload 语义完全一致，不存在客户端分叉；上一轮 3 处改动对
级联保存均安全。核检中发现一处**加固缺口**：`DispatchService` 会把投递记录写入
`clip-storage/dispatch-records/{clipId}.json`（UUID id、非剪藏数据），该目录未纳入
`EXCLUDED_DIR_NAMES`，一旦产生文件会被 `getAllJsonFiles()` 误当剪藏扫描，污染桌面端与
插件端共享的 `/api/clip/list` 并触发 `Long` 反序列化警告。本轮计划：修复该缺口 + 执行级联保存的端到端验证。

## 当前状态分析
- **双端统一入口（核检关键结论）**：
  - 浏览器插件：[clip-main.js](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/browser-extension/clip-main.js#L166) `axios.post(\`${API_BASE_URL}/add\`, requestBody)`；分类取值来自 `/categories` 接口：一级 value（如 `work`）或二级 value（如 `work-company`）或空串（落入收件箱），见该文件 212–241 行。
  - 桌面端：[clip-form.js](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/frontend/clip-form.js#L143) 同样从后端 `/categories` 加载分类树并提交 category value。
  - 两端指向**同一个** `POST /api/clip/add`，`@CrossOrigin("*")` 已允许插件跨域；后端为唯一事实源。
- **级联分类映射**：[FileStorageService.getCategoryPath()](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/backend/src/main/java/com/example/clip/service/FileStorageService.java#L206-L238) 将二级 value（如 `work-company`）映射到 `storagePath/work/公司事务`，一级 value 映射到 `storagePath/work`，空映射到 `default`。
- **上一轮改动（已验证对级联安全）**：
  1. `readClipArrayFromFile()` object 分支改返回可变 `ArrayList` —— 仅影响外层 `removeIf`，读侧（list/category/workflow/search，只迭代不改）不受影响。
  2. `EXCLUDED_FILE_NAMES` 追加 `records.json`、`feature-points.json` —— `product-dev/260810.json`（真实剪藏日期文件）不受影响，仅排除该目录下 `records.json`（UUID id 的需求归档）。
  3. `ClipController.addClip()` 判空兜底 —— 仅防御分支。
- **本次核检发现的新缺口**：[DispatchService.java](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/backend/src/main/java/com/example/clip/service/DispatchService.java#L233) 将投递记录写入 `clip-storage/dispatch-records/{clipId}.json`（UUID id、字段结构与 `ClipContent` 不同，属独立数据类型），而 `EXCLUDED_DIR_NAMES` 未含 `dispatch-records`。若产生该目录文件，`getAllJsonFiles()` 会将其混入共享剪藏数据源 → 长期污染两端的 `/api/clip/list` 及 ID 分配。
- 参考数据：`product-dev` 下现有 `260810.json`（空数组，真实剪藏）与 `records.json`（UUID 需求归档）；当前 `dispatch-records` 目录尚未产生，属潜在风险。

## 变更方案

### 1) 加固：排除 Dispatch 投递记录目录（唯一代码改动）
**文件**: `backend/src/main/java/com/example/clip/service/FileStorageService.java`，`EXCLUDED_DIR_NAMES`（约 309–316 行）
**改法**: 追加 `dispatch-records`，使投递记录（UUID id）永不进入共享剪藏扫描：
```java
private static final Set<String> EXCLUDED_DIR_NAMES = Set.of(
        "todoList", "knowledge", "knowledge-base", "topic", "vault", "learning-plan",
        "tmp", "editor", "weekly-report", "weeklyReport", "clip-organized",
        "dispatch-records",   // 内容投递记录（DispatchRecord，UUID id，非剪藏数据）
        ".tmp", ".trash", ".git", ".obsidian", ".dsh", ".index",
        ...
);
```
说明：`DispatchService` 读取走自身路径 `dispatch-records/{clipId}.json`（见 DispatchController GET /records），
不受本项目影响；仅避免它被误当作剪藏。属纯加固，不改变任何剪藏读写路径。

> 若确认无需改动，可仅保留验证步骤；但该目录缺失会埋下后患，建议纳入。

### 2) 级联保存端到端验证（核检核心，无代码）
编译并重启后端 jar 后，用 HTTP 直连后端模拟两端同一请求，覆盖 3 类级联分类并断言结果：

| # | category | workflowStatus | 预期落盘文件 | 预期异常 |
|---|----------|---------------|--------------|---------|
| 1 | `work-company`（二级） | inbox | `clip-storage/work/公司事务/{yyMMdd}.json`（数组, 自增 id） | 无 |
| 2 | `work`（一级） | inbox | `clip-storage/work/{yyMMdd}.json` | 无 |
| 3 | ``（空，收件箱） | inbox | `clip-storage/default/{yyMMdd}.json` | 无 |

请求样例（Invoke-WebRequest，等效浏览器插件 `clip-main.js` 提交的 payload）：
```powershell
Invoke-WebRequest -Method Post -Uri http://localhost:8081/api/clip/add -ContentType 'application/json' -UseBasicParsing `
  -Body '{"type":"store-only","source":"browser","category":"work-company","workflowStatus":"inbox","content":"核检-级联保存","title":"级联核检","useAiTags":false}'
```
判定：返回 `{"id":<正数>,"status":"success"}`；后端日志该请求后无 ERROR 栈、无
`UnsupportedOperationException`、无 `Cannot deserialize value of type java.lang.Long from String ...` 警告。

### 3) 双端回归抽查
- `GET /api/clip/list`（桌面端与插件 `clip-main.js` 均使用）返回正常，不含 `product-dev/records.json` 与
  `dispatch-records` 内容，二级分类剪藏正确出现在列表。
- `GET /api/clip/workflow/inbox` 能看到用例 2/3 的剪藏；`GET /api/clip/category/work-company` 能读到用例 1。
- 读取旧格式单对象 `clip-storage/hobby/260719.json` 的剪藏仍正常展示（verify 可变列表读侧无回归）。

## 假设与决策
- 假设：桌面端与插件端无需差异适配——核检证明两者 payload 与接口一致，级联问题全部落在后端存储层。
- 决策：将 `dispatch-records` 也纳入目录排除（与 `records.json` 同级同因），统一"非剪藏数据不得进入共享扫描"的边界。
- 决策：不做数据迁移——单对象文件与 `records.json` 保持原样，仅调整读取/扫描语义。
