**一句话**：做一套"**判断力账本**"，先给自己（产品/研发）用，攒厚了再外化——**不做 C 端功能，不加新页面**。

## 二、分维度实施（A–H，全部落到已核实文件）

### A. 数据模型：迭代记录 四字段 → 六字段（最小侵入）

**现状（已核实）**：`feature-point-iterations.json` 每条记录的四字段 = `title / problem / solution / outcome` + `source`。
落在 [FeaturePointIterationService.java](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/backend/src/main/java/com/example/clip/service/FeaturePointIterationService.java#L92-L98) 的 `add()`（`item.put(...)` 段落）。

**改动（数据契约）**：新增两字段，二者**均可选**：

| 字段 | 含义 | 结构（**已决策：纯文本**） |
|---|---|---|
| `expectation` | **事前预测** | `string`（一段文字，含"我预期……"） |
| `surprise` | **预测误差 + 归因** | `string`（一段文字，含"实际……，偏在……，因为……"） |

> **决策**：先用**纯文本**跑一版（改动最小、直接渲染），验证有用了再考虑结构化。置信度暂并入 `expectation` 文本里（如"高置信"），不做独立字段。

**兼容规则**：
- 老记录无这两字段 → **前端隐藏、后端读时按空处理**，不迁移、不改历史 JSON。
- 写入路径：`/api/workspace/feature-points/iterations/ai-session` 的入参与 DTO **两端同步**新增两字段。
- 后端若为 TS：在迭代记录类型定义里加 `expectation?` / `surprise?` 两个 optional 字段即可。

**Why**：文章说"判断力的原料是预测与被校准的结果"。迭代记录本来就是"我做了什么（problem/solution/outcome）"，缺的正是"我当初**预期**什么、结果**出乎意料**在哪"——补这两格，一条记录就从"干活日志"升级为"判断样本"。

### B. 采集时机：机制优先于意志（零新增触发点）

**B1 前移预测**：任务开始时写"我的预测"。
- 落点：`TODO/{需求}/` 的需求起点（`01-需求分析.md` 模板）加一格「**预期与验收假设**」。
- 与 A 的 `expectation` 对应：需求起点写预测 → 归档时带入迭代记录。

**B2 后置复盘**：挂在**已有**的"推送后自动归档"上，不新增触发点。
- 现状（已核实）：[git-commit-workflow SKILL](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/.trae/skills/git-commit-workflow/SKILL.md#L28-L34) 第 5 步「推送成功后自动归档」已有两条链：① 产品概览迭代记录（`trae-session-archive`）、② HARNESS devlog/bug（`harness-archive`）。
- 改动：在链① 的提炼里，**追加产出 `expectation` / `surprise`**（从本次会话 + 需求文档的"预期"里提炼）。

**B3 复用现成格式**：`commit_history.log` 兼容追加 `#教训:xxx`。
- 现状（已核实）：[git-push.ps1](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/scripts/git-push.ps1#L131-L137) 第 5 步写入 `$stamp | $m`。
- 改动：给脚本加**可选参数** `-Lesson "<一句话>"`；提供时写成 `$stamp | $m #教训:<...>`。
- **向后兼容**：现有解析按 `|` 切分不受影响，`#教训:` 是行尾附加段；不传参数则行为完全不变。

> **Why**：这就是"机制优先于意志"——不靠我自觉去复盘，而是**提交推送这个已经肌肉记忆的动作**顺手把教训写下来。

### C. 品味机制：走 topic 通道做"对照实验"（零后端改动）

**现状（已核实）**：[smart-ingest](file:///f:/30_Projects%20(行动项目)/31_Work%20(主要工作)/ai_coding/.trae/skills/smart-ingest/SKILL.md#L184-L199) 已支持 `POST /api/topic`，字段含 `tags`。

**落地**：
1. 同一设计让 Agent 出 **3 个异质候选** → 各存为一条 `topic`，打标签 `对照组` + `品味`。
2. 我以用户视角**选一个**，并写"**为什么它更好**"（存进该 topic 的 `content` 或 `summary`）。
3. 产品侧只需一个**按标签聚合的视图**（见 D 的 tab），把历次"对照组"摊开比较。

**零后端改动**：完全复用既有 topic 入库能力与 tags 字段。

> **Why**：文章说品味靠"大量比较 + 实际创作"。用 Agent 低成本批量造对照组，正是"以用户视角挑"的训练器。

### E. 代码规范（符合 user_rules）

- 后端新增字段：**必须带日志 + 中文注释**；读旧记录缺字段时 `log.warn` 一句、按空处理。

> **Why**：这正是文章说的"把『我错了』变成『我为什么会错』"。审计脚本是**机制的手**——不写教训就报红，逼出归因。

### G. 收益/外部资本（务实版，明确不做 C 端）

- **不做 C 端产品**，先把"判断力账本"**自用攒厚**：迭代记录（含 expectation/surprise）越多，越能反推出。
- **导出"个人/团队研发画像"**：从迭代记录 + HARNESS 聚合出"预测命中率 / 常见误判类型"。
- **再外化方法论**：把"判断力账本"的做法写成模板/内容（少数派、公众号）——这才是文章说的"外部资本"，而不是又一个自娱自乐的产品。

## 五、假设与决策

1. **纯文档交付**：本文不改任何代码；后端后续转 TS，故只给"数据契约 + 行为"。
2. **可选项优先**：`expectation`/`surprise` 均可选，缺省隐藏，绝不打断现有流程。
3. **不做 C 端、不加新页面、默认不打扰**（延续 ADR 0004 的"轻量、核心功能优先"原则）。
4. **不做置信度门控**：`expectation` 为纯文本、置信度并入文本；不引入任何"数值置信度"做功能门控（延续 ADR 0004 边界）。
